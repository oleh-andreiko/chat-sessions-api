# Chat sessions API

Невеликий REST-сервіс: користувач веде окремі чат-сесії з OpenAI. Сервіс тримає
історію діалогу в PostgreSQL, підмішує її в кожен наступний запит, зберігає
token usage з відповіді OpenAI і рахує вартість кожної взаємодії.

Тестове завдання для Pro Business Center, Крок 3. Технічний план — у [PLAN.md](PLAN.md).

**Стек:** Python 3.14, FastAPI, PostgreSQL 16 (Docker), SQLAlchemy, OpenAI SDK.

---

## Запуск

**1. База даних**

```bash
docker compose up -d
```

Postgres підіймається на порту **5433** (не 5432), щоб не конфліктувати з іншими
локальними базами. Готовність можна перевірити через `docker ps` — контейнер
`testtask-db` має бути `healthy`.

**2. Оточення**

```bash
cp .env.example .env
```

У `.env` треба вписати `OPENAI_API_KEY`. Решта значень уже придатні для локального
запуску. `.env` у `.gitignore` і в репозиторій не потрапляє.

> Якщо `OPENAI_API_KEY` уже є в системному оточенні, він має пріоритет над `.env`:
> `load_dotenv()` не перезаписує наявні змінні.

**3. Залежності та сервер**

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe -m uvicorn app.main:app --reload
```

На Linux/macOS шлях до інтерпретатора — `.venv/bin/python`.

Сервіс підніметься на `http://127.0.0.1:8000`:

- `http://127.0.0.1:8000/ui` — проста сторінка для ручної перевірки: створити
  сесію, надіслати кілька повідомлень, побачити токени й накопичену вартість;
- `http://127.0.0.1:8000/docs` — інтерактивна документація (Swagger UI).

**Схема БД** створюється автоматично при старті застосунку
(`Base.metadata.create_all`). Окремий крок міграції не потрібен.

> `create_all` створює лише відсутні таблиці й не змінює наявні. Якщо база
> лишилася від попередньої версії сервісу, її треба перестворити:
> `docker compose down -v && docker compose up -d`. Для реального деплою
> потрібен Alembic — див. «Відомі обмеження».

## Модель і тарифи

Модель за замовчуванням — **`gpt-4o-mini`**. Кожне повідомлення може попросити
іншу, і вартість рахується за тарифами саме тієї моделі. Публічні тарифи OpenAI,
звірені **27.08.2026**:

| Модель | Input / 1M | Output / 1M |
|---|---|---|
| `gpt-4o-mini` | $0.15 | $0.60 |
| `gpt-4.1-nano` | $0.10 | $0.40 |
| `gpt-4.1-mini` | $0.40 | $1.60 |

```
cost = prompt_tokens / 1_000_000 * 0.15
     + completion_tokens / 1_000_000 * 0.60
```

Ставки лежать у `app/services/pricing.py`, у словнику `MODEL_PRICING`. Додати
модель — це один запис у словнику; роути й логіка чату не змінюються. Модель без
запису в таблиці цін піднімає явну помилку, а не рахується безкоштовною.

### За яким саме ідентифікатором рахується вартість

OpenAI розгортає псевдонім у датований знімок: на запит `gpt-4o-mini` відповідь
приходить від `gpt-4o-mini-2024-07-18`. Тарифікація йде **за псевдонімом**, який
попросив клієнт, бо прайс публікується саме за псевдонімами — датованої назви
в таблиці цін не було б, і кожен запит падав би.

Датований ідентифікатор при цьому зберігається окремо, у колонці
`messages.resolved_model`, щоб завжди було видно, яка модель фактично відповіла.

### Категорії usage, які не враховуються

OpenAI повертає в `usage` більше, ніж використовує ця формула. Свідомо не враховані:

- **`prompt_tokens_details.cached_tokens`** — кешовані вхідні токени тарифікуються
  вдвічі дешевше ($0.075 за 1M). Сервіс рахує весь input за повною ставкою, тому
  для повторюваних промптів **вартість може бути завищена**.
- **`completion_tokens_details.reasoning_tokens`** — для reasoning-моделей. У
  `gpt-4o-mini` їх немає; при переході на таку модель формулу треба доповнити.

## API

| Метод | Шлях | Призначення |
|---|---|---|
| `POST` | `/sessions` | Створити сесію |
| `POST` | `/sessions/{id}/messages` | Надіслати повідомлення, отримати відповідь, usage і cost |
| `GET` | `/sessions/{id}` | Сесія, **повна історія** і накопичена вартість |
| `POST` | `/sessions/{id}/reset` | Почати новий контекст, зберігши той самий `id` |
| `GET` | `/sessions/{id}/messages` | Тільки активна історія, без агрегатів |
| `GET` | `/health` | Перевірка живучості |
| `GET` | `/ui` | Сторінка для ручної перевірки API |

### Приклади запитів

**1. Створити сесію**

```bash
curl -X POST http://127.0.0.1:8000/sessions \
  -H "Content-Type: application/json" \
  -d '{"title": "context check"}'
```

```json
{"id":"0ee98902-ef1d-45f6-9e5a-7f8676f9f2eb","title":"context check","model":"gpt-4o-mini","created_at":"2026-08-25T14:41:32.714749Z"}
```

**2. Надіслати повідомлення**

```bash
curl -X POST http://127.0.0.1:8000/sessions/0ee98902-ef1d-45f6-9e5a-7f8676f9f2eb/messages \
  -H "Content-Type: application/json" \
  -d '{"content": "What is my name and my favourite number?"}'
```

```json
{
  "message": {"id":4,"role":"assistant","content":"Your name is Oleh and your favourite number is 47.","model":"gpt-4o-mini","prompt_tokens":42,"completion_tokens":12,"cost":"0.00001350","created_at":"2026-08-25T14:41:36.129019Z"},
  "model":"gpt-4o-mini","prompt_tokens":42,"completion_tokens":12,"cost":"0.00001350"
}
```

**3. Сесія з історією і накопиченою вартістю**

```bash
curl http://127.0.0.1:8000/sessions/0ee98902-ef1d-45f6-9e5a-7f8676f9f2eb
```

```json
{
  "id":"0ee98902-ef1d-45f6-9e5a-7f8676f9f2eb","title":"context check","model":"gpt-4o-mini",
  "messages":[ ... ],
  "total_prompt_tokens":66,"total_completion_tokens":13,"total_cost":"0.00001770"
}
```

**4. Обрати модель для конкретного повідомлення**

```bash
curl -X POST http://127.0.0.1:8000/sessions/<id>/messages   -H "Content-Type: application/json"   -d '{"content": "Reply with just OK.", "model": "gpt-4.1-nano"}'
```

```json
{"message":{"id":6,"role":"assistant","content":"OK","model":"gpt-4.1-nano","resolved_model":"gpt-4.1-nano-2025-04-14","prompt_tokens":17,"completion_tokens":1,"cost":"0.00000210"},"model":"gpt-4.1-nano","prompt_tokens":17,"completion_tokens":1,"cost":"0.00000210"}
```

Поле `model` необов'язкове: без нього береться модель сесії.

**5. Скинути контекст сесії**

```bash
curl -X POST http://127.0.0.1:8000/sessions/<id>/reset
```

```json
{"id":"<той самий id>","title":"reset test","model":"gpt-4o-mini","current_generation":2,"messages":[],"total_prompt_tokens":0,"total_completion_tokens":0,"total_cost":"0"}
```

### Помилки

Усі помилки мають один формат:

```json
{"error": {"code": "session_not_found", "message": "Session ... does not exist."}}
```

| Ситуація | Код | `code` |
|---|---|---|
| Неіснуюча сесія | 404 | `session_not_found` |
| Порожній `content`, невалідний UUID | 422 | `invalid_input` |
| Помилка OpenAI (таймаут, rate limit, 5xx) | 502 | `upstream_error` |
| Клієнт попросив непідтримувану модель | 400 | `unsupported_model` |
| Модель самої сесії відсутня в таблиці цін | 500 | `pricing_not_configured` |
| База даних недоступна | 500 | `database_error` |

## Структура

```
app/
  main.py                    # застосунок, роутери, обробники помилок
  config.py                  # налаштування з .env
  db.py                      # engine і сесія БД
  models.py                  # таблиці sessions і messages
  schemas.py                 # валідація запитів і форма відповідей
  errors.py                  # доменні помилки та їх HTTP-вигляд
  routers/sessions.py        # тільки HTTP, без бізнес-логіки
  services/chat.py           # історія → OpenAI → вартість → запис
  services/openai_client.py  # єдине місце, що знає про SDK
  services/pricing.py        # ціни і розрахунок
  static/index.html          # сторінка /ui, без збірки і залежностей
tests/
  test_pricing.py            # розрахунок вартості
```

Роути не містять бізнес-логіки. Знання про ціни живе тільки в `pricing.py`,
знання про зовнішній API — тільки в `openai_client.py`.

## Рішення, які варто пояснити

**Вартість зберігається в кожному повідомленні, а не перераховується.** Ціни
OpenAI змінюються. Якби зберігалися тільки токени, історична вартість старих
сесій «попливла б» за поточним прайсом.

**Тип `numeric(14,8)`, не `float`.** Для грошей похибка двійкового представлення
накопичується. Вісім знаків після коми, а не шість: коротка взаємодія на
`gpt-4o-mini` коштує близько $0.000007, і шість знаків з'їдали б помітну частину.

**Обидва повідомлення обміну пишуться однією транзакцією після успішної
відповіді OpenAI.** Якби питання писалося до виклику, при падінні API в базі
лишилося б повідомлення без відповіді — і наступний запит підхопив би його
в контекст, спотворивши діалог.

**Історія сортується за `(created_at, id)`, не тільки за часом.** Пара
«питання-відповідь» пишеться в одній транзакції, тому їхні часові мітки
відрізняються на мікросекунди або збігаються. `id` робить порядок однозначним.

**Reset не видаляє повідомлення, а переводить сесію в наступне покоління.**
У `sessions` є `current_generation`, у `messages` — `generation`. Активна історія
й усі агрегати рахуються лише за поточним поколінням, тому після reset історія
порожня, а `total_cost` дорівнює нулю. Старі рядки лишаються в таблиці.

Обрано саме так, а не фізичне видалення, тому що вся модель обліку вартості
будувалася на тому, що `cost` фіксується в момент відповіді й не перераховується
заднім числом — щоб історія витрат лишалася правдивою. Видалення на reset
знищувало б саме той запис про реально витрачені гроші, який ці колонки й
існують, щоб зберігати. Витрати за весь час сесії дістаються одним запитом:

```sql
SELECT SUM(cost) FILTER (WHERE generation = s.current_generation) AS active,
       SUM(cost) AS lifetime
FROM messages m JOIN sessions s ON s.id = m.session_id
WHERE s.id = '<id>';
```

**Модель обирається на рівні повідомлення, а не сесії.** Модель сесії лишається
значенням за замовчуванням; параметр `model` у запиті перевизначає її тільки для
цього повідомлення. Непідтримувана модель відсікається **до** виклику OpenAI —
інакше запит був би оплачений, а потім усе одно завершився помилкою. Те саме
перевіряється і при створенні сесії: інакше сесію з неіснуючою моделлю можна було б
створити успішно, а потім отримувати помилку на кожному повідомленні.

**Агрегати рахуються при читанні, а не зберігаються лічильниками.** Денормалізація
дала б швидкість, не потрібну на цьому обсязі, ціною ризику розсинхрону.

**З'єднання з БД перевіряється перед використанням (`pool_pre_ping`) і має
таймаут підключення.** Після перезапуску Postgres у пулі залишаються сокети,
які виглядають відкритими, але вже мертві; без перевірки перший же запит падає,
а без таймауту запит до зупиненої бази висить замість того, щоб чесно
повернути помилку. З цими двома налаштуваннями сервіс переживає перезапуск
бази без власного рестарту.

## Тести

```bash
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
.venv/Scripts/python.exe -m pytest
```

37 тестів у трьох файлах:

| Файл | Що перевіряє |
|---|---|
| `test_pricing.py` | тарифи трьох моделей і формулу вартості |
| `test_api.py` | коди відповідей, форму відповіді, тіла помилок |
| `test_chat.py` | що саме бачить модель: контекст, обрізання, покоління |

Тести працюють проти **справжнього PostgreSQL**, але в окремій базі `app_test`,
яка створюється автоматично. SQLite був би простішим, але схема спирається на
типи Postgres (`UUID`, `numeric`), і тоді тести доводили б працездатність там,
де код ніколи не виконується.

Виклик OpenAI підмінений: ці тести не про поведінку моделі, а про те, які
повідомлення ми вирішили їй надіслати і що робимо з usage у відповіді. Заглушка
записує кожен виклик, тому можна перевірити сам контекст, а не лише результат.

Тестові залежності лежать окремо в `requirements-dev.txt`, щоб список
runtime-залежностей залишався рівно тим, що потрібне сервісу для роботи.
`pytest.ini` додає корінь проєкту в `sys.path`, тому `pytest` працює незалежно
від того, з якої теки його запустили.

Робочу базу тести не чіпають: перевірено окремо — записаний у `app` рядок
переживає повний прогін без змін.

### Чи ловлять ці тести помилки

Зелений набір тестів нічого не доводить, поки не показано, що він уміє червоніти.
Перевірено мутаціями — код ламався навмисно, по одній зміні за раз:

| Внесена поломка | Результат |
|---|---|
| прибрано фільтр поколінь в активній історії | тест впав |
| прибрано обрізання історії до `MAX_HISTORY_MESSAGES` | тест впав |
| прибрано перевірку моделі перед викликом OpenAI | тест впав |
| вартість рахується за моделлю сесії, а не обраною | тест впав |
| `reset` не збільшує покоління | тест впав |

П'ять із п'яти. Після перевірки код відновлювався з git і звірявся з комітом.

## Відомі обмеження

Свідомо залишено поза scope через таймбокс і межі завдання:

- **Немає авторизації.** Сесії не прив'язані до користувача — прямо дозволено умовами тестового.
- **Немає міграцій.** Схема створюється при старті. Для реального деплою потрібен Alembic.
- **Немає тестів на паралельні запити.** Порядок записів перевірявся окремим
  навантажувальним прогоном (80 одночасних обмінів), але в наборі тестів цього
  сценарію немає — він потребує кількох процесів, а не одного.
- **Немає retry для OpenAI.** Помилка одразу повертається як 502.
- **Історія обрізається за кількістю повідомлень** (`MAX_HISTORY_MESSAGES`, типово 20),
  а не за токен-бюджетом. Простіше, але менш точно: 20 довгих повідомлень і
  20 коротких коштують по-різному.
- **Модель фіксується при створенні сесії** і не змінюється в її межах.
- **`cached_tokens` не враховуються** — див. розділ про тарифи.
- **Ціни оновлюються вручну.** OpenAI не віддає прайс через API.
- **Немає streaming відповідей** — у постановці не згадувався.
- **Паралельні повідомлення в одну сесію отримують недетермінований контекст.**
  Кожен запит читає історію до того, як інші встигли записати свою, тому
  одночасні відправлення бачать різні зрізи діалогу. Порядок записів при
  цьому не страждає: пара «питання-відповідь» лишається суміжною. Перевірено
  на 80 одночасних обмінах. Для послідовної роботи, як у звичайному чаті,
  проблеми немає; блокування сесії не додавав, бо задача його не вимагає.
- **Сторінка `/ui` — мінімальна:** один HTML-файл без збірки і залежностей,
  без збереження сесії між перезавантаженнями сторінки.
