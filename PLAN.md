# Крок 2. Архітектура та план реалізації

**Стек:** Python, FastAPI, PostgreSQL (SQLAlchemy), OpenAI API.

## 1. Сутності

**`sessions`** — `id` (UUID, PK), `title` (nullable), `model` (фіксується при створенні),
`created_at`.

**`messages`** — `id` (bigserial, PK), `session_id` (FK → `sessions`, ON DELETE CASCADE),
`role` (`user` / `assistant`), `content`, `model` (nullable, для відповіді),
`prompt_tokens` / `completion_tokens` (nullable), `cost` (numeric(12,6), nullable),
`created_at`. Індекс `(session_id, created_at)`.

Usage і cost лежать на рівні повідомлення, бо ціни OpenAI змінюються: вартість фіксується
в момент відповіді, інакше історія старих сесій перераховувалася б за поточним прайсом.
Агрегатів у `sessions` немає — сума рахується `SUM` по `messages` при читанні;
денормалізація дала б непотрібну на цьому обсязі швидкість ціною ризику розсинхрону.

## 2. REST endpoints

| Метод | Шлях | Призначення |
|---|---|---|
| `POST` | `/sessions` | Створити сесію. Body: `model`, `title` (опційні; модель за замовчуванням — з конфігу) |
| `POST` | `/sessions/{id}/messages` | Body: `content`. Виклик OpenAI, запис пари «питання-відповідь», повертає відповідь + usage + cost обміну |
| `GET` | `/sessions/{id}/messages` | Історія в хронологічному порядку |
| `GET` | `/sessions/{id}` | Сесія з агрегатами: сумарні токени і `total_cost` |

Останній закриває вимогу «показувати токени і накопичену вартість», тримаючи агрегати
окремо від історії.

## 3. Контекст попередньої історії

При `POST /sessions/{id}/messages`: перевірка існування сесії → читання попередніх
повідомлень за `(created_at, id)` → мапінг у `[{"role": ..., "content": ...}]` з новим
повідомленням у кінці → виклик OpenAI.

Сортування включає `id`, бо пара «питання-відповідь» пишеться однією транзакцією:
`created_at` можуть збігтися, і порядок ролей став би невизначеним. Той самий порядок —
у видачі історії.

У контекст беруться останні `MAX_HISTORY_MESSAGES` повідомлень (з конфігу): без обмеження
вартість кожного запиту росте разом з історією, а довга сесія впирається в context window.
Обрізання за токен-бюджетом точніше, але для цього обсягу надлишкове.

## 4. Usage і розрахунок вартості

Токени з відповіді OpenAI пишуться в рядок `assistant`-повідомлення разом із назвою моделі
та `cost`. Розрахунок — один раз, до запису в БД:

```
cost = prompt_tokens / 1_000_000 * input_price
     + completion_tokens / 1_000_000 * output_price
```

Тип `Decimal` (у БД `numeric`), не `float`: для грошей похибка двійкового представлення
накопичується.

## 5. Model-specific pricing

Окремий модуль `services/pricing.py`, ізольований від роутів і логіки чату: словник
`MODEL_PRICING` вигляду `{model: {"input": Decimal, "output": Decimal}}` і функція
`calculate_cost(model, prompt_tokens, completion_tokens) -> Decimal`.

Нова модель — один запис у словнику, без правок роутів і сервісу. Невідома модель піднімає
явну помилку, а не мовчазний нульовий cost, інакше сесія тихо рахувалася б безкоштовною.
Модуль не залежить від БД і FastAPI, тому тестується ізольовано. Ціни вносяться вручну —
API їх не віддає.

## 6. Обробка помилок

Єдиний формат: `{"error": {"code": ..., "message": ...}}` через `exception_handler` FastAPI.

| Ситуація | Код | Поведінка |
|---|---|---|
| Неіснуюча сесія | `404` | Перевірка до зовнішніх викликів — не витрачати запит до OpenAI |
| Некоректний input (порожній `content`, невалідний UUID) | `422` | Валідація Pydantic-схемами, до входу в сервіс |
| Помилка OpenAI (таймаут, rate limit, 5xx) | `502` | Явний таймаут; лог із `session_id`; деталі назовні не течуть |
| Невідома модель у pricing | `500` | Явна помилка конфігурації |
| Помилка БД | `500` | Відкат транзакції, лог |

Обидва повідомлення обміну пишуться однією транзакцією **після** успішної відповіді
OpenAI: якщо писати питання до виклику, при падінні API залишиться повідомлення без
відповіді, і наступний запит підхопить його в контекст.

## 7. Структура модулів

```
app/
  main.py                    # FastAPI app, роутери, обробники помилок
  config.py                  # налаштування з .env
  db.py                      # engine, сесія, залежність для DI
  models.py                  # SQLAlchemy-моделі
  schemas.py                 # Pydantic-схеми запитів і відповідей
  errors.py                  # доменні винятки + обробники
  routers/sessions.py        # тільки HTTP: валідація, виклик сервісу, коди
  services/chat.py           # історія → OpenAI → розрахунок → запис
  services/openai_client.py  # обгортка над SDK: таймаут, помилки
  services/pricing.py        # ціни і розрахунок вартості
```

Роут не містить бізнес-логіки. Логіка діалогу — в `chat.py`, ціни — тільки в `pricing.py`,
знання про зовнішній API — тільки в `openai_client.py`.

## 8. Припущення

- Авторизації немає (правило Кроку 1); сесії не прив'язані до користувача.
- Модель фіксується при створенні сесії. Поле `model` у `messages` усе одно зберігається —
  щоб історична вартість лишалася коректною, якщо припущення зміниться.
- Історія обрізається за кількістю повідомлень, не за токен-бюджетом.
- Валюта — USD, як у прайсі OpenAI; конвертації немає.
- System prompt і streaming не реалізуються — у постановці не згадані.
- Ціни вносяться вручну з офіційного прайсу.

## 9. Питання до уточнення

1. Чи потрібно змінювати модель у межах сесії, чи достатньо фіксувати при створенні?
2. Чи потрібен endpoint зі списком усіх сесій?
3. Чи є очікування щодо ліміту на кількість повідомлень або бюджет сесії?
