# Крок 2. Архітектура та план реалізації

**Стек:** Python, FastAPI, PostgreSQL (SQLAlchemy), OpenAI API.

---

## 1. Сутності та ключові поля

### `sessions`

| Поле | Тип | Призначення |
|---|---|---|
| `id` | UUID, PK | Ідентифікатор сесії |
| `title` | text, nullable | Необов'язкова назва |
| `model` | text | Модель OpenAI, зафіксована при створенні сесії |
| `created_at` | timestamptz | Час створення |

### `messages`

| Поле | Тип | Призначення |
|---|---|---|
| `id` | bigserial, PK | Ідентифікатор повідомлення |
| `session_id` | UUID, FK → sessions, ON DELETE CASCADE | Належність до сесії |
| `role` | text (`user` / `assistant`) | Роль у діалозі |
| `content` | text | Текст повідомлення |
| `model` | text, nullable | Модель, якою згенеровано відповідь (для `assistant`) |
| `prompt_tokens` | int, nullable | З `usage` відповіді OpenAI |
| `completion_tokens` | int, nullable | З `usage` відповіді OpenAI |
| `cost` | numeric(12,6), nullable | Вартість, розрахована в момент відповіді |
| `created_at` | timestamptz | Час створення |

Індекс: `(session_id, created_at)` — під вибірку історії та побудову контексту.

**Чому usage і cost лежать на рівні повідомлення, а не сесії.** Ціни OpenAI змінюються з часом. Якщо зберігати тільки токени й перераховувати вартість заднім числом за поточним прайсом, історична вартість старих сесій попливе. Тому вартість фіксується в момент відповіді.

**Чому в `sessions` немає лічильників-агрегатів.** Накопичена вартість і токени рахуються `SUM` по `messages` при читанні. Денормалізовані лічильники дали б швидше читання, але створюють ризик розсинхрону з реальними даними. Свідомо обраний простіший варіант: обсяг даних тестового цього не потребує.

## 2. REST endpoints

| Метод | Шлях | Призначення |
|---|---|---|
| `POST` | `/sessions` | Створити сесію. Body: `model` (опційно, інакше — дефолт з конфігу), `title` (опційно). Повертає сесію |
| `POST` | `/sessions/{session_id}/messages` | Надіслати повідомлення. Body: `content`. Викликає OpenAI, зберігає пару «питання-відповідь», повертає відповідь + usage + cost цього обміну |
| `GET` | `/sessions/{session_id}/messages` | Історія повідомлень сесії у хронологічному порядку |
| `GET` | `/sessions/{session_id}` | Сесія з агрегатами: сумарні `prompt_tokens`, `completion_tokens`, `total_cost` |

Останній endpoint — під вимогу «показувати використання токенів і накопичену вартість сесії». Винесений окремо, щоб історія повідомлень не змішувалася з агрегатами.

## 3. Контекст попередньої історії

При `POST /sessions/{id}/messages`:

1. Перевірка існування сесії.
2. Читання попередніх повідомлень сесії, впорядкованих за `(created_at, id)`.
3. Мапінг у формат OpenAI: `[{"role": ..., "content": ...}, ...]`, у кінець додається нове повідомлення користувача.
4. Виклик OpenAI з цим масивом.

**Чому сортування за `(created_at, id)`, а не тільки за часом.** Питання користувача
і відповідь асистента пишуться однією транзакцією, тому їхні `created_at` можуть
збігтися. За однаковим часом порядок рядків не визначений, і ролі в контексті могли б
помінятися місцями. `id` (bigserial) монотонно зростає і робить порядок однозначним.
Той самий порядок використовується і при видачі історії через `GET`.

**Обмеження історії.** У контекст беруться останні `MAX_HISTORY_MESSAGES` повідомлень (значення з конфігу). Без обмеження історія росте лінійно, разом з нею росте вартість кожного наступного запиту, а довга сесія врешті впирається в context window моделі. Обрізання по кількості повідомлень — найпростіший достатній варіант; обрізання за токен-бюджетом точніше, але для обсягу цього завдання надлишкове.

## 4. Зберігання usage і розрахунок вартості

OpenAI повертає `usage` з `prompt_tokens` і `completion_tokens`. Обидва значення записуються в рядок `assistant`-повідомлення разом із розрахованим `cost` і назвою моделі.

Розрахунок виконується один раз — у момент отримання відповіді, до запису в БД. Формула:

```
cost = prompt_tokens / 1_000_000 * input_price
     + completion_tokens / 1_000_000 * output_price
```

Тип — `Decimal` (у БД `numeric`), не `float`: для грошових величин накопичення похибки двійкового представлення неприйнятне.

## 5. Model-specific pricing

Виноситься в окремий модуль `services/pricing.py`, ізольований від роутів і від логіки чату.

```python
MODEL_PRICING = {
    "<model-name>": {"input": Decimal("..."), "output": Decimal("...")},
}

def calculate_cost(model: str, prompt_tokens: int, completion_tokens: int) -> Decimal:
    ...
```

Ціни заповнюються з офіційного прайсу OpenAI на момент реалізації — API їх не віддає, тому це єдине місце, яке доведеться оновлювати вручну.

Властивості рішення:

- додавання нової моделі — це один запис у словнику, без зміни коду роутів чи сервісу чату;
- невідома модель піднімає явну помилку, а не мовчазний нульовий cost — інакше сесія тихо рахувалася б безкоштовною;
- модуль чистий і не залежить від БД чи FastAPI, тому тестується ізольовано.

## 6. Обробка помилок

Єдиний формат тіла помилки для всіх випадків: `{"error": {"code": ..., "message": ...}}`, через `exception_handler` FastAPI.

| Ситуація | Код | Поведінка |
|---|---|---|
| Неіснуюча сесія | `404` | Перевірка до будь-яких зовнішніх викликів — не витрачати запит до OpenAI на завідомо помилковий шлях |
| Некоректний input (порожній `content`, невалідний UUID) | `422` | Валідація на рівні Pydantic-схем, до входу в сервіс |
| Помилка OpenAI API (таймаут, rate limit, 5xx) | `502` | Виклик обгорнутий з явним таймаутом; помилка логується з `session_id`; назовні не протікають внутрішні деталі |
| Невідома модель у pricing | `500` | Явна помилка конфігурації, не мовчазний нуль |
| Помилка БД | `500` | Транзакція відкочується, помилка логується |

**Порядок запису.** Повідомлення користувача і відповідь асистента записуються **однією транзакцією після** успішної відповіді OpenAI. Якщо писати питання до виклику API, то при падінні виклику в базі залишиться повідомлення без відповіді — і наступний запит підхопить його в контекст, спотворивши діалог.

## 7. Структура модулів

```
app/
  main.py                    # FastAPI app, реєстрація роутерів і обробників помилок
  config.py                  # налаштування з .env
  db.py                      # engine, сесія, залежність для DI
  models.py                  # SQLAlchemy-моделі
  schemas.py                 # Pydantic-схеми запитів і відповідей
  errors.py                  # доменні винятки + обробники
  routers/
    sessions.py              # тільки HTTP: валідація, виклик сервісу, коди відповідей
  services/
    chat.py                  # оркестрація: історія → OpenAI → розрахунок → запис
    openai_client.py         # обгортка над SDK: таймаут, обробка помилок
    pricing.py               # ціни моделей і розрахунок вартості
```

Принцип поділу: роут не містить бізнес-логіки — приймає запит, викликає сервіс, віддає відповідь. Логіка діалогу живе в `chat.py`, знання про ціни — тільки в `pricing.py`, знання про зовнішній API — тільки в `openai_client.py`.

## 8. Припущення

- **Авторизація не реалізується** — згідно з правилами Кроку 1. Сесії не прив'язані до користувача.
- **Модель фіксується при створенні сесії** і не змінюється в її межах. Поле `model` у `messages` при цьому зберігається — щоб історична вартість лишалася коректною, якщо це припущення згодом зміниться.
- **Історія обрізається за кількістю повідомлень**, а не за токен-бюджетом.
- **Валюта — USD**, як у прайсі OpenAI. Конвертація не робиться.
- **System prompt не задається** — у постановці про нього не сказано.
- **Streaming відповідей не потрібен** — у постановці не згадано.
- **Ціни вносяться вручну** з офіційного прайсу.

## 10. Строки та ризики

**Фінальний дедлайн не змінився — 30.08, 20:00.**

**ETA на Крок 3 (реалізація): 2–2,5 години.**

Ризики:

- **Актуальність цін.** OpenAI не віддає прайс через API, тому таблиця цін оновлюється вручну і з часом застаріває. Ізоляція в окремому модулі мінімізує вартість оновлення, але не усуває саму потребу.
- **Зростання вартості за довгими сесіями.** Кожен наступний запит несе всю попередню історію, тому вартість обміну зростає з довжиною діалогу. Обрізання історії обмежує це, але робить діалог «забудькуватим» — компроміс свідомий.
- **Робота з зовнішнім API.** Таймаути й rate limits OpenAI впливають на час відповіді сервісу. Закладено явний таймаут і коректний код помилки; retry-логіка не реалізується, щоб не виходити за рамки завдання.
